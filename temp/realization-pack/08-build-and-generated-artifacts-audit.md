# Build And Generated Artifacts Audit

## Executive summary

The repo’s build system includes a significant generated-artifact layer. The core issue is not just that generation exists; it is that some generated surfaces are:

- tracked
- some are ignored
- some are canonical outputs
- some are legacy or questionable
- some have stale-artifact risk

This needs to be classified clearly before restructuring.

## Artifact classification table

| Artifact / directory | Current role | Tracked? | Current status | Notes |
|---|---|---|---|---|
| `registry.json` | Derived registry manifest | Yes | Derived tracked artifact | Root manifest generated by registry scanner. |
| `public/registry/*.json` | Per-item install payloads + indexes | Yes | Derived tracked artifact | Public install/search/docs support surface. |
| `content/registry/**/*` | Generated registry docs MDX | Ignored | Derived ignored artifact | Input to Fumadocs docs layer. |
| `.source/*` | Fumadocs generated runtime files | Ignored | Derived ignored artifact | Required runtime dependency for registry docs/search. |

| `public/llms-full.txt` | Extended machine-readable summary | Yes | Derived tracked artifact | Same. |

| `public/registry/index.json` | Full registry index | Yes | Derived tracked artifact | May be partially orphaned if docs are the only runtime browse surface. |
| `public/registry/index-slim.json` | Slim registry browse index | Yes | Derived tracked artifact | Same. |
| `_map.ts` under collected components | Generated import map | Yes | Derived tracked artifact | Used to resolve collected previews. |

## Current generated sizes observed

- `public/registry`: ~1.4M
- `content/registry`: ~440K
- `.source`: ~44K

These are not catastrophic, but they are large enough to deserve explicit ownership and cleanup rules.

## Current pipeline shape

`npm run build` currently does:

1. `generate-posters`
2. `generate-registry-json.mjs`
3. `build-registry.mjs`
4. `post-process-registry.mjs`
5. `generate-registry-mdx.mjs`
6. `generate-llms-txt`
7. `next build`

Separately, CI and successful clean-main local verification also require:

8. `npx fumadocs-mdx`

## Current clean-main build result

In the fresh worktree, after `npm ci`, the clean-main build succeeds:

- poster generation succeeds
- registry generation succeeds
- registry docs generation succeeds
- Fumadocs source generation succeeds
- `next build` succeeds

This means the clean-main baseline is healthy. The earlier build hang is not a baseline truth of `main`.

## Current generated-output issues

### 1. Mixed tracked/ignored ownership

The repo mixes:

- tracked generated public artifacts
- ignored generated docs/source artifacts

That is acceptable, but only if the build contract is explicit and deterministic.

### 2. Registry docs prerequisite is operationally real

Even though clean-main succeeds once dependencies are installed, registry docs still rely on:

- `content/registry`
- `.source`

These are ignored generated inputs and should be treated as first-class build products in docs and verification.

### 3. Potential stale artifact classes

Potential stale artifacts include:

- removed registry items lingering in `public/registry`
- generated docs pages for removed registry items
- stale `.source` files after docs source changes

The realization pass should make cleanup and ownership rules explicit.

### 4. Story/demo artifact leakage in the registry

Current clean-main registry generation still emits `.story` registry items and then filters/skips them later in downstream layers. This is a canonical-scan problem, not just a presentation issue.

### 5. Warning noise

The clean-main pipeline emits **63 registry validation warnings** during `post-process-registry.mjs`.

Current warning classes:

- missing recommended `dependencies`
- missing recommended `registryDependencies`
- warnings on `.story` artifacts
- warnings on simple utility/component items that intentionally omit optional arrays

These should be treated as their own hardening problem because warning noise masks real regressions.

### 6. Operational infrastructure

`package.json` runs a postinstall patch:

```bash
node scripts/patch-r3f-perf.mjs
```

This patches `r3f-perf` for Turbopack compatibility on every `npm install`. It is fragile but intentional infrastructure and should be explicitly inventoried in the realization pass.

## Classification decisions for the clean pass

### Source of truth

Should remain:

- `experiment.json`
- article MDX/frontmatter
- collected component metadata
- registry curation config

### Derived tracked artifacts

Should likely remain tracked unless the repo intentionally changes policy:

- `registry.json`
- `public/registry/*.json`
- `public/llms.txt`
- `public/llms-full.txt`
- generated posters

### Derived ignored artifacts

Should remain generated and ignored, but with a clearly owned generation step:

- `content/registry`
- `.source`

### Stale-candidate outputs

Need explicit cleanup rules:

- `public/registry` item JSONs
- generated docs for removed registry entries
- possibly generated collected preview maps

### Dead / questionable artifacts

Need explicit decision:

- `index.json`
- `index-slim.json`
- story-item JSON files

## Required build-contract decisions

The realization pass must settle:

- which generated artifacts are canonical outputs
- which must exist before runtime code executes
- which are ignored but required
- which are stale-risk candidates requiring cleanup
- whether the grid/index artifacts are still first-class or just historical leftovers

## Recommendation

- Keep native source models where they are.
- Keep tracked public generated artifacts if they are part of the public/runtime contract.
- Keep `content/registry` and `.source` as generated artifacts, but make their ownership explicit.
- Consolidate registry generation into one orchestrated pipeline with cleanup and phase boundaries.
- Triage warning noise explicitly before using registry build output as a trustworthy verification signal.
